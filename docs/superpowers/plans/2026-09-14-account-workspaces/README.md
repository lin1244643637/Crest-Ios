## 1. 最终使用效果

一个手机号对应一个账号。每个账号始终拥有个人空间，可以另外加入多个租户工作空间。账号、手机号、密码保持同一份；角色、数据范围和业务能力属于当前工作空间。

例如同一个账号可以处于以下状态：

| 当前空间 | 本空间角色 | 能做什么 | 历史与用量归属 |
| --- | --- | --- | --- |
| 个人空间 | 无租户角色 | 基础文字聊天、查看本人聊天历史、管理本人账号、申请加入工作空间 | 本人 |
| A 公司工作空间 | member | 已获授权的租户聊天、文件、对账、分析等 | A 公司 |
| B 公司工作空间 | admin | B 公司业务能力，加上成员及工作空间管理 | B 公司 |

个人空间不查询租户知识库、文件、报表、对账结果、记忆、聊天历史、连接器或业务数据库。个人账号即使已经加入公司，也必须切换到该公司工作空间才能使用其业务入口。租户工作空间同样不读取个人聊天历史。

用户手动输入或粘贴到个人聊天框的文字可以参与本次对话；系统不根据文字里出现的公司名、文件 ID 或链接自动读取任何租户资源。首版个人聊天不开放附件、外部连接器、联网检索或业务工具。

## 2. 完整用户流程

1. 输入手机号，调用只读预检接口；此时不发短信、不创建验证挑战。
2. 未注册：发送个人注册验证码，验证后直接创建账号、建立设备会话、进入个人聊天主页。无须用户名、密码或邀请码。
3. 已注册且有密码：进入密码登录，可在已验证手机号支持时选择验证码登录。
4. 已注册但无密码：直接使用验证码登录。历史联系方式冲突进入账号处理流程，不自动合并或绑定。
5. 服务端返回 `has_password=false` 时，在账号区域展示“完善密码”，可跳过；设置成功后各空间共用这份密码。
6. 用户使用租户编码申请加入；审批中仍只有原有权限。批准后工作空间列表增加该租户，不退出个人空间、不迁移聊天、不自动切换。
7. 用户主动切换工作空间，服务端核验成员资格并更新本设备会话，返回新访问令牌和能力。其他独立登录的设备不受影响。
8. 退出或被移出租户，只移除该成员资格，账号、个人聊天和其他工作空间继续存在。

新注册默认个人空间；已有租户用户首次升级默认原租户以保持现有体验。后续会话恢复使用该设备最后的空间。全新设备登录：有兼容默认租户且资格仍有效则使用它，否则进入个人空间。不要把当前空间存成 `User.current_tenant_id`。

## 4. 数据模型

### 4.1 账号与成员资格

| 实体 | 字段与约束 | 规则 |
| --- | --- | --- |
| `users` | `id`、唯一用户名、唯一规范化手机号、验证时间、可空密码哈希、`token_version` | 手机号和密码为账号级。`has_password` 从已保存的哈希是否存在派生，禁止本地布尔值作为依据 |
| `users` 兼容列 | `tenant_id` 改可空；保留原 `role` | 仅用于迁移和旧客户端默认空间。不能继续用于新授权，不能随空间切换改写 |
| `tenants` | 复用现有租户 | 每个租户就是一个公司工作空间，无须再建通用 `workspaces` 表 |
| `tenant_memberships` | 复用历史表：`id/user_id/tenant_id/role/status/requested_at/approved_at/approved_by/reason` | 为 `(user_id, tenant_id)` 加唯一约束，验证后补用户与租户外键；`active` 才能使用空间 |
| `tenant_join_requests` | 保留现有审批记录；`from_tenant_id` 可空 | 新申请从个人或任何空间发起均可，来源不参与授权；默认不向目标公司披露用户属于哪些其他公司 |

个人空间由账号本身表示，没有租户行，也不写入 `tenant_id="personal"` 或 `"default"`。`role=null` 表示当前个人空间；无需给用户新增 `role=personal`，也不把 `account_type` 当作永久身份。

成员资格状态收敛为 `active/suspended/removed`；历史表若已有 `pending/rejected`，视为无权限历史记录，不直接升级为 active。审批待办继续用 `tenant_join_requests`。迁移先检查重复、孤立行和历史状态，再建立约束；不能猜测实际数据状态。

个人注册生成无手机号含义的唯一内部用户名，显示层继续复用已有 username。个人显示名编辑可后续独立增加，不阻塞本次流程。

### 4.2 设备会话与访问令牌

复用 `auth_refresh_sessions`。`user_id` 表示账号所有者；增加 `workspace_type=personal|tenant`、`context_version`、`refresh_token_version`；`tenant_id` 改为可空的当前空间租户 ID。约束 personal 对应 NULL，tenant 对应有效非空 ID。

新的刷新凭据使用版本化格式 `a2.<session_id>.<secret>`，数据库仍只存 secret 的哈希；刷新凭据本身不携带租户。`session_id` 只是查找键，必须校验哈希、撤销、空闲和绝对过期。现有三段租户刷新凭据仅在受控兼容阶段兑换为 a2，不能在解析失败时猜测其他格式。

访问令牌保留 `user_id/sub/token_version` 等现有字段，新增 `sid/workspace_type/context_version`，并带当前 `tenant_id`。数据库中的成员角色是授权真值；令牌和响应中的角色、capabilities 仅是快照。保留现有平台管理员 scope 隔离。

切换与刷新在同一会话行上串行执行：

- 切换校验账号、设备会话、目标资格及 `expected_context_version`，原子更新空间并递增 context_version，签发访问令牌；不轮换刷新 secret，不延长会话寿命。
- 刷新锁定会话后校验当前 secret，再轮换；返回数据库中最新空间，不覆盖切换结果。并发使用同一旧 secret 只能一次成功。
- 所有工作空间请求验证 sid、会话状态与 context_version；切换前的访问令牌不能继续发起该设备的租户操作。账号设置接口也验证会话版本，但不要求租户仍有效。
- 若成员资格失效或租户停用，业务接口拒绝；账号会话仍可刷新，刷新明确降为个人空间、递增版本并返回 `workspace_change_reason`。账号仍能列出空间及主动切回个人。
- 全局重置密码、账号联系方式安全变更按既有安全策略递增账号 token_version，并按 user_id 撤销所有空间的设备会话；移除一个租户成员只影响该租户权限。
- 移动端切换响应丢失时用原刷新凭据恢复真实上下文；不能根据点击动作自行推测已切换。已轮换刷新凭据的响应丢失沿用失效重新登录流程，不放宽单次消费。

统一数据库锁顺序：涉及多个实体时按租户行（多租户按 ID 排序）→ 用户行 → 成员资格/审批行 → 设备会话行。单纯刷新只锁会话行；任何拿到会话锁的路径不得反向申请前面的行锁。上线前以并发测试核对实际事务实现。

同一 Web Cookie 会话的多个标签页共享当前空间，这是本设计的明确语义；独立登录产生不同 sid，因此不同设备可处于不同空间。

### 4.3 个人聊天与用量

新增 `personal_chat_sessions`：`id/user_id/title/created_at/updated_at`，索引 `(user_id, updated_at, id)`，支持游标分页。

新增 `personal_chat_messages`：`id/session_id/user_id/turn_id/role/content/status/request_hash/created_at`。状态为 `streaming/completed/failed/cancelled`。每次逻辑发送生成 `turn_id`，唯一约束 `(user_id, turn_id, role)`；会话增加 `(id,user_id)` 唯一键，消息用复合外键保证会话与所有者一致。服务端校验重试请求指纹，阻止同一 turn_id 改正文或改会话。

个人表无 tenant_id 列。所有读写用当前账号 user_id 加资源 ID；跨账号或错误类型 ID 统一 404。缓存使用 `personal:<user_id>:<session_id>`；禁止复用只按 session_id 或默认租户命名的业务缓存。

复用 `llm_usage_records`，添加 `workspace_type`，允许 personal 行的 tenant_id=NULL，要求个人行的 user_id 非空。已有用量回填 tenant；租户行仍要求 tenant_id 非空。租户账单和管理员汇总只读取对应租户行。实际个人用量记账号，不混入任意租户余额；本期配置额度，不增加付费套餐系统。

## 5. 认证与权限边界

复用公共令牌验证逻辑，保留三种明确依赖：

| 依赖 | 校验内容 | 使用入口 |
| --- | --- | --- |
| `get_current_account`（新增） | 账号、token_version、sid、会话版本及有效期，拒绝平台 token | 本人资料、首次设密、工作空间列表/切换、申请加入 |
| `get_current_personal_user`（新增薄依赖） | 账号认证成功，当前空间 personal 且 tenant_id=NULL | `/basic-chat/*` |
| `get_current_user`（保留名字） | 账号认证、当前空间 tenant、活跃租户、活跃成员资格；返回成员角色 | 现有租户业务、`require_admin` |

个人入口不能只依赖 `get_current_account` 后接受任意空间的令牌，否则在公司界面可悄悄写入个人历史。所有查询使用服务端认证上下文，客户端 body/header 中的 tenant_id 不能授予权限。现有 `get_tenant_id/extract_tenant_id` 读取 Header 的路径要检查调用方，用户业务路径改用认证上下文。

既有聊天、SSE、文件上传下载、sessions、对账、分析、知识库、报表、任务、Agent runs、通知、自动化和连接器继续使用租户门禁。平台接口、外部回调和内部 Worker 保留各自独立认证，按真实调用检查，不能机械改成个人可访问。

租户业务查询及 JOIN 仍显式包含 tenant_id。会话、个人偏好等本来属于用户的租户资源同时包含 user_id。权限检查发生在业务查询、缓存读取、对象存储访问和派发任务之前。

已发起的租户长任务保留创建时不可变的租户上下文，切空间不会搬迁或冒充取消已产生的业务动作。切换中的 SSE/前台请求由客户端取消；后端在下一次发送数据或执行有副作用工具前检查上下文版本/资格，失效就终止。结果下载仍重新鉴权。无法收回已经发送给客户端的数据。

## 6. 加入与管理工作空间

复用租户编码与管理员审批。提交申请只生成待办；批准在一个事务内把成员资格创建或恢复为 active 并记录审批人；重复批准不重复创建资格。拒绝只修改请求状态。个人空间和其他租户资格不受影响。

已有账号使用邀请凭据加入：先登录，再显式接受邀请并核验有效期、用途和指定联系方式（若有绑定）；确认后仅增加成员资格。未注册用户先完成个人手机号注册，再接受邀请。原邀请注册入口保留兼容，但注册成功也必须创建同样的成员资格，不能只写 `User.tenant_id`。

成员列表、成员角色、人数统计全部按 membership 查询。A 公司管理员对该账号的管理权限仅限 A 公司成员资格，不能读取个人聊天、修改全局密码/手机号、删除账号或操作 B 公司角色。租户管理员新建账号的旧入口转为邀请流程；旧“直接设置用户密码”请求明确提示使用邀请，不静默赋予全局账号控制权。

成员移除/暂停立即影响该租户后续请求。最后一位 active admin 不能退出、被移除或降权；同租户并发管理操作锁租户行检查。租户中的历史文件、对话和业务数据仍留在租户，不随账号移除而删除，也不自动给其他成员扩大可见范围。

平台管理员能力仍单独授权。平台全局账号删除、租户删除的实现须适配多成员关系和个人数据的已有保留规则；租户删除不得级联删除账号，平台管理界面要区分全局账号和租户成员操作。

## 7. 个人基础聊天实现

新增 `basic_chat.py` 路由和 `basic_chat_service.py` 服务，复用现有模型适配器、`TextDelta/MetadataEvent/Completed/Failed` 事件及 SSE 编码。服务只组装系统提示、本人该会话的有界历史和本次文字。

模型选择使用 `ModelRouter.personal_adapter()`，从服务端个人默认配置创建现有 adapter，不走 `_load_tenant_model_override`。不调用 ChatOrchestrator、Owner Agent、租户 Model Gateway、KB、RAG、用户业务记忆或工具注册。安全边界由调用路径保证，提示词只说明当前能力。

首版包含创建/列表/读取/重命名/删除个人会话、文字发送、流式展示、主动停止与错误重试。复用已存在界面结构；服务端对历史分页、上下文长度、输出长度和并发做有界限制。使用现有 Redis 原子能力按 user_id 限流，额度数值由配置给出，不写死商业套餐。

首次发送先原子保存用户消息及 streaming 助手占位，再调用模型；完整持久化后才发 Completed。相同 turn_id 不重复调用模型：进行中返回 409，完成后回放已保存结果，失败/取消返回原状态。用户明确重试生成使用新 turn_id，避免网络重传重复计费。断流关闭上游并标记终态；进程崩溃遗留 streaming 行按明确超时恢复为 failed。

个人调用显式建立 `workspace_type=personal, tenant_id=None, user_id=当前账号` 的用量上下文，finally 恢复外层 ContextVar。现有 `None=继承` 约定需要新增显式重置入口，不能直接把 None 传入旧函数。保留现有用量异步持久化链路并测试；额度按请求原子预留和释放，不能依赖延迟到账的用量记录防并发超额。

## 8. iOS 交互与状态

复用 `ChatView`、聊天组件、侧栏和设置页。添加小型 `WorkspaceContext/WorkspaceSummary/AccountProfile` 模型；API 层显式分派 personal 与 tenant 路径，无需复制完整个人首页和 ChatView。

侧栏账号区域提供工作空间选择：个人空间始终可见，下面列出已加入的公司；显示当前空间名称与角色，另有加入工作空间入口。个人空间只显示基础聊天相关入口与通用文字建议；公司空间显示原业务入口。能力受角色控制，UI 展示不能替代服务端授权。

`SessionStore` 保存服务端返回的账号资料、has_password、当前空间与版本；刷新凭据继续存 Keychain。切换成功后原子更新访问令牌和上下文。切换响应没有 refresh_token，不能复用当前要求 refresh_token 非空的完整登录 apply 方法。

切换时进入短暂切换状态，取消聊天流、历史请求和所有前台轮询；清空当前消息、选中会话、工作空间草稿与历史内存。数据任务捕获 `user_id/workspace_key/context_version`；晚到响应只允许写回相同上下文。RootView 用该组合重建聊天状态，避免同账号 A 公司历史闪现在 B 公司或个人空间。

同空间 401 可刷新后重试可重放请求；刷新或切换导致 workspace_key/context_version 改变时，旧请求取消，不把其正文、会话 ID 或上传任务自动重试到新空间。尤其不能让现有 `withAuthenticatedSession` 的自动重试跨空间执行。

首次设密成功刷新服务端资料，隐藏提示，保持当前页和设备登录。`must_change_password` 保留既有强制改密含义，与“从未设置密码”分开；忘记密码继续独立验证码重置和会话撤销。

## 9. 发布与迁移

先完成模型、成员回填、认证隔离和兼容读写，再开放个人注册和多空间切换。迁移不得把历史聊天搬到个人空间，也不得按相同手机号静默合并多个旧账号。

1. 检查实际 Alembic heads、表是否存在、重复成员、孤立租户、手机号冲突和现有角色。结果只输出计数与脱敏摘要；异常记录阻止相关回填，交给确定性处理清单。
2. 新增可空账号字段与会话字段，复用 membership 表补约束，回填现有有效用户租户关系为 active；与历史 suspended/removed 冲突时停止该条回填，不复活已撤销资格。
3. 部署成员读写、版本化会话与新认证，旧接口也产生成员资格。兼容期间所有账号/成员写入走同一事务，迁移和在线新增覆盖无遗漏；切换前核对差异计数为零。
4. 新增个人聊天表与用量作用域，更新 Worker 序列化消费。旧 Worker 不能接收新字段；Worker 兼容上线后才生产 personal 用量消息。
5. 在工作空间功能开启前关闭无 sid/context_version 的旧访问令牌。过渡期仅按明确原租户及现有有效 membership 接受旧令牌；到截止时间统一拒绝，客户端刷新兑换新格式。旧刷新凭据有独立兼容截止时间，跨过旧格式分支不得绕过撤销。
6. 新 iOS 验证恢复、切换、验证码注册和聊天后，按功能开关开放。旧租户客户端继续收到原有 token/username/user_id/tenant_id/role/refresh_token 字段；当前租户字段取当前空间值。个人返回 NULL 租户需新版客户端，旧版新账号入口需版本能力拦截。
7. 保留兼容列一段观察期；只有调用方审计不再依赖 `User.tenant_id/User.role` 授权，才在后续单独迁移删除。首版不做清理性大改。

回退优先关闭新注册/新切换等入口并使用兼容新结构的修复版本。已存在个人账号、多个成员资格或 NULL 用量后，不能直接降级至旧代码或恢复 NOT NULL；数据迁移标记为有条件可逆，不删除个人数据凑回旧结构。

## 10. 交付边界

本轮交付可实施设计及文件清单，不代表新增接口已经可调用。实施包含完整账号生命周期、多租户切换、个人文字聊天及原业务隔离；不附带新支付系统、个人附件系统、全局通用权限框架或新的聊天引擎。

完整实施与验收门槛见 [02-implementation-and-acceptance.md](02-implementation-and-acceptance.md)。
